1. What EduPortal Is

EduPortal (branded in the browser tab as StudyMate — EduPortal Core) is a self-contained school management and learning platform built as a single HTML file with no build step and no framework. Everything — markup, styling, and application logic — lives in one index.html, which makes it something you can host almost anywhere a browser can reach: GitHub Pages, a custom domain, a plain web server, or even opened straight off a hard drive.

The same file adapts itself to two kinds of institutions — schools (primary/secondary) and tertiary institutions (colleges/universities) — and to seven roles: Owner, Admin/Principal, Teacher, Student/Learner, plus supporting tertiary roles such as Registrar-facing views. Which features a person sees is decided at login, not by separate builds.

Because it is one file, "installing" EduPortal anywhere is really just publishing that file (plus a couple of optional companion files) to a web host. The rest of this manual is about doing that properly, and about what to configure so every copy — on every domain it's published to — behaves like the full product instead of a stripped-down preview.

3. Where EduPortal Works Best

EduPortal is built to run anywhere, but it is not equally capable everywhere. The file detects its own hosting environment at boot and turns features on or off accordingly. In order, from most to least capable:

3.1 Best: GitHub Pages + Firestore (production)

This is the environment the app is designed around, and where it should live for real school use:

  • Every visitor gets the same live data — enrolments, materials, whiteboard boards, timetables — because Firestore (or an equivalent online backend) is the shared source of truth, not each visitor's own browser.
  • The app auto-detects that it is on a *.github.io URL and infers its own GitHub owner/repo, so GitHub-based sync (registry sync, full backup sync, custom-domain CNAME management) works with almost no manual configuration beyond a Personal Access Token.
  • Real-time features — the collaborative whiteboard's live drawing, viewer-count-aware sync — only run in this configuration; they are explicitly disabled in preview/offline contexts.
  • A custom domain (including a "www." domain) can be layered on top of GitHub Pages via a CNAME file, and the app keeps that domain in sync automatically.

3.2 Good, with caveats: a custom domain or your own web server

Serving the same file from a plain web server or a custom domain not proxied through GitHub Pages works, but the automatic "which GitHub repo am I" detection has nothing to key off, so GitHub sync must be configured manually (owner, repo, branch, and token) in the Owner Console rather than being inferred. Firestore-backed sync still works normally once Firebase is configured, since that part of the app doesn't care what domain it's served from.

3.3 Limited: opened from disk, or previewed inside Claude.ai

If the file is opened directly from a local disk, or rendered as a preview inside an environment like Claude.ai, several things are deliberately scaled back:

  • No GitHub repo can be inferred (there is no GitHub Pages URL to read it from).
  • Live, frame-by-frame whiteboard streaming is disabled — students still get autosaved snapshots into Class Materials, but not real-time drawing.
  • If no Firestore project is configured, the app quietly falls back to that one browser's local storage, so data will not be visible to anyone opening the app on a different device.

This tier is fine for demos, screenshots, and local testing, but it is not where a school should run day-to-day operations.

4. What's Needed to Use It on Every Website (Full Multi-Site Setup)

Because EduPortal is one static file, the same copy can be published to as many places as needed — a GitHub Pages URL, one or more custom domains, or mirrored onto another static host — and every copy can share the same live data, provided the following are configured once. These are the pieces that make the difference between "a copy that works" and "a copy that's fully wired up":

4.1 A shared online backend (Firestore)

Without this, each browser/device only ever sees its own local data. With it, every deployment of the file — regardless of which domain served it — reads and writes the same shared records.

  1. Create a free Firebase project at console.firebase.google.com (the Spark/free plan is sufficient at this scale).
  2. Register a Web app under Project settings → General → Your apps, and copy the generated firebaseConfig values into the FIREBASE_CONFIG block near the top of index.html.
  3. Create a Firestore database (production mode, region close to your users).
  4. Publish Firestore security rules that open read/write on the single eduportal_kv collection the app uses (the exact rule block is documented inline in the file, immediately above FIREBASE_CONFIG).
  5. Optional but recommended for real access control: deploy the two Cloud Functions (mintAuthToken, mintOwnerToken) referenced in functions/index.js, and paste the resulting base URL into FIREBASE_FUNCTIONS_BASE. Until this is filled in, login checks happen only in the browser, which deters casual access but is not real security.

4.2 GitHub sync, secured through a proxy

The Owner Console can mirror the school registry and full backups to a GitHub repository via the GitHub Contents API. On GitHub Pages, the owner and repo are inferred automatically from the URL; on any other domain they must be entered manually in the Owner Console's GitHub Registry Sync panel. Either way, a Personal Access Token is required, and — as the in-app warning notes — a token typed directly into this static page is visible to anyone with access to that browser.

To close that gap, route every GitHub Contents API call through a small Cloudflare Worker proxy that holds the token server-side instead of in the browser. This is tracked as ongoing work on this project: the proxy needs to sit in front of every Contents API call uniformly, not just some of them, so no code path accidentally sends a raw token to api.github.com from the client.

4.3 Custom domains

Any domain — apex or "www." — can front the GitHub Pages deployment by adding a CNAME file to the repository. Once set, the app reads that CNAME back (via a no-token, read-only fetch from raw.githubusercontent.com) so the Owner Console's Custom Domain field auto-fills correctly in any browser, not just the one it was originally typed into.

4.4 One shared link format across every domain

Regardless of which domain a given deployment lives on, individual schools are addressed the same way: a ?school=<id> query parameter (for example, ?school=buhleni-high-school) routes a visitor straight into that school's context, sets the browser tab title and link-preview (Open Graph / Twitter Card) tags to that school's name, and is what search engines and chat-app link previews read. This is what makes it possible to hand out a clean per-school link no matter which domain is currently serving the file.

4.5 Checklist — full multi-site readiness

Before treating a deployment as production-ready:

  • ☐ Firebase project created and FIREBASE_CONFIG filled in (not the placeholder values)
  • ☐ Firestore rules published
  • ☐ Cloud Functions deployed and FIREBASE_FUNCTIONS_BASE set, for real login security
  • ☐ GitHub sync configured (auto on GitHub Pages; manual owner/repo/branch/token elsewhere)
  • ☐ GitHub token routed through the Cloudflare Worker proxy, not stored raw in the browser
  • ☐ Custom domain CNAME set, if applicable, and confirmed to auto-fill in a second browser
  • ☐ SEO/meta tags verified per school by opening a ?school= link and checking the tab title

5. Day-to-Day Notes

  • Owner Console: create/manage schools, broadcast announcements to all schools at once, and generate a sitewide sitemap.
  • Class Materials: teachers upload files; students download them from the same tab.
  • Collaborative Whiteboard: live drawing requires the production (GitHub Pages + Firestore) deployment; elsewhere it still autosaves snapshots into Class Materials.
  • Tertiary institutions additionally get a public Apply Now form, a Faculties directory, a Google-Knowledge-Panel-style School Profile page, and a Degree Audit page.
  • Passwordless sign-in is supported, with in-portal password management for anyone who prefers a password.
